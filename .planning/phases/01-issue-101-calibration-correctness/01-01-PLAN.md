<objective>
Stop a broad cause with zero observed deaths from silently killing the calibration, without shrinking the misclassification matrix, and remove those causes from every result surface while disclosing that they were removed.

Purpose: R1. On the issue's own file this is the entire defect — a zero-count cause sits on the simplex boundary, path correction fails on its first iteration, lambda returns at its ceiling, and no calibration is applied.
Output: `donotcalib` built from the observed death counts and passed to `vacalibration()` from both job paths; zero-death causes filtered out of the result payload and the exported CSVs; a disclosure line in the results summary.
</objective>

<mechanism>
This section is verified fact, measured against the installed CRAN vacalibration 2.2 while planning. Do not re-derive it, and do not substitute a different mechanism — but DO re-read the package source if you need a detail that is not written here (`Rscript -e 'writeLines(deparse(vacalibration::vacalibration))'` and the same for `vacalibration:::modular_vacalib_prior` / `modular_vacalib_fixed`).

**The fix is the `donotcalib` argument.** `vacalibration()` accepts `donotcalib` (a NAMED LIST keyed exactly like `va_data`, one character vector per algorithm) and `donotcalib_type` (default `"learn"`).

1. `modular_vacalib_prior()` computes the path-correction line search over ONLY the calibrated subset: it renormalizes `puncalib[k, !donotcalib_tomodel[k, ]]` and back-solves on that submatrix. A zero-count cause listed in `donotcalib` is therefore off the simplex, and the search proceeds normally.
2. `donotcalib_type = "learn"` UNIONS our list with the causes it learns are unreliable (`diff(range(column)) <= nocalib.threshold` on the row-normalized matrix). It does NOT replace them. So passing `donotcalib` does not disable the package's own reliability rule.
3. The misclassification matrix is sliced to `names(va_data_tomodel[[k]])`, i.e. the COLUMN NAMES of the one-hot matrix — not to the causes with nonzero counts. Keeping all 9 (child) / 6 (neonate) columns keeps the matrix full-size, which is why the reliability decision for `malaria` is unchanged. `Mmat_tomodel` stays `1 x 9 x 9`.
4. Supplying `donotcalib` SUPPRESSES the package default `if (is.null(donotcalib)) donotcalib = "other"`. Every entry we build must therefore include `"other"` explicitly, or `other` silently starts being calibrated.
5. The package validates each entry against `names(va_data_tomodel[[k]])` and `stop()`s otherwise, so entries must be derived from `colnames()` of the matrix we pass — never from raw uploaded cause strings.
6. If the exclusions leave one or fewer calibratable causes, the package emits `** Cannot calibrate <algo>`, sets `result$calibrated[k]` FALSE, leaves `lambda_calibpath[k]` as NA, and returns `pcalib_postsumm` rows equal to `p_uncalib` (a point mass). `path_correction_stalled(NA)` is FALSE, so without a new guard the dashboard would present that run as calibrated.

**Measured on `frontend/public/sample_eava_child.csv` (2383 records, child, Mozambique, EAVA, `missmat_type = "prior"`), planning-time probe:**

| arm | `donotcalib` | lambda | `donotcalib_tomodel` | malaria |
|---|---|---|---|---|
| today | not passed | 0.99 (stalled no-op) | `other` | calibrated but the whole run is a no-op |
| the fix | `list(eava = c("other", "injury", "nn_causes"))` | 0.39 | `injury, other, nn_causes` | calibrated: 0.0843 -> 0.0381 |

`other_infections` moves 0.3021 -> 0.4531, matching REQUIREMENTS.md's "30% -> 45.3%". `injury` and `nn_causes` are exactly 0.0000 in both the uncalibrated and calibrated vectors, and the remaining seven sum to ~1.0000, so dropping them from display distorts nothing (already verified — do not add a re-verification task).

**Why Mozambique, and why this is the reliability test:** on `CCVA_missmat$child$eava$asDirich`, the row-normalized `malaria` column range is 0.1163 over the full 9-cause slice and 0.0681 over the 7 observed causes — straddling the 0.1 `nocalib.threshold`. Mozambique is the ONLY one of the eight countries where it straddles (every other country is 0.16-0.31 on both slices), which is why the issue reproduces there. Those two numbers are deterministic (no MCMC, no sampling) and can be asserted exactly.

**lambda is not reproducible.** The search averages 1000 unseeded `rdirichlet` draws and the `seed` argument only reaches `rstan::sampling` afterwards. Never assert an exact lambda. Assert the outcome: not stalled, and calibration actually moved the estimates.
</mechanism>

<constraints>
- Do NOT shrink the cause set handed to `vacalibration()`. `build_broad_matrix()` and `safe_cause_map()` keep producing all 9 (child) / 6 (neonate) columns. Passing only the observed causes is the WRONG fix and un-calibrates malaria.
- Do NOT pass `donotcalib_type`, `nocalib.threshold`, or `path_correction` — leave every one at its package default.
- Do NOT depend on the package author's forthcoming `exclude_zero_causes` argument. When it ships with a default, `donotcalib` remains valid, so this fix degrades gracefully.
- Zero-death exclusion is deliberate and must be DISCLOSED, unlike the unmapped-cause case in project memory `project_reject_unrecognized_causes` where dropping is forbidden. A zero-count cause has no records to lose; an unmapped cause does. Keep `assert_all_causes_mapped()` exactly as it is.
- Do NOT renormalize the remaining causes after dropping the zero ones.
- Simplest code. No new module, no new abstraction layer, no config flag to turn this on and off.
</constraints>
