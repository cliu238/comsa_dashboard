<objective>
Retract our own false-precision framing on the backend: restore the credible-interval bounds of a stalled run in `calibration_summary.csv`, delete the `ci_unreliable` field whose only purpose was to suppress them, and relabel a stalled row as the uncertainty of an uncalibrated estimate.

Purpose: R2. This is our error, shipped in PRs #115, #119 and #121. The suppression rested on comparing a stalled run against the same input with `path_correction = FALSE` — a different calibration that propagates misclassification uncertainty. A stalled run applied NO calibration, so it correctly carries only sampling error. Verified against the multinomial sampling error of the uncalibrated proportions: per-cause ratios 0.98-1.02 across every calibrated cause. The intervals were right; the label was wrong.
Output: corrected `build_stall_fields()` and `build_summary_df()`, and a rewritten section 28 that asserts the corrected framing.
</objective>

<retraction_scope>
What is TRUE and must be preserved:
- Stall detection is correct. `LAMBDA_CEILING`, `path_correction_stalled()`, `build_lambda_map()`, `stalled_algorithms()` and `any_stalled()` keep their current logic, including the two different ceilings (0.99 on the default `missmat_type = "prior"`, 1.01 on `"fixed"`, which is reachable from JobForm's "Propagate" checkbox). A stalled run really did apply no calibration.
- lambda is still reported for provenance, and the ensemble still has no lambda of its own.
- A point-mass interval (`lower == upper == postmean`, produced for every cause the package did not calibrate — `other` is always one) is still suppressed. That rule has nothing to do with the stall and stays.
- `calibration_declined` (added by plan 01-01) stays.

What is WRONG and must go:
- `ci_unreliable` as a payload field and as a suppression trigger. Its only meaning was "these intervals carry false precision", which is the claim being retracted. Delete the field rather than leaving it unread — CLAUDE.md requires deleting legacy rather than keeping a dead version around. Older stored jobs still contain it in their JSONB result; nothing reads it, so they simply start showing their intervals, which is the correct retraction.
- Blanking `calibrated_lower` / `calibrated_upper` in `calibration_summary.csv` because a run stalled.
- The `ci_omitted_reason` column name and its wording. Bounds are no longer omitted for a stall, so the name is false. Replace it with `interval_note`.
- Every code comment that asserts the retracted claim. The long comments at `backend/jobs/utils.R` lines 666-676, 709-721 and 757-766 state that a stalled run's intervals are "~7x TOO TIGHT" / "not meaningful" / "carry false precision". Rewrite them to state what is actually true: at lambda near the ceiling the misclassification matrix is treated as nearly known, no calibration is applied, and the returned interval is the uncertainty of the uncalibrated estimate (sampling error only) — which is why it is narrower than a successful calibration's, and why that is correct rather than suspicious.

Not in scope: `path_correction = FALSE` is not an acceptable fix (the package author reports a posterior projection problem, which is what motivated path correction). Do not add such an option.
</retraction_scope>

<wording>
Use these strings so the tests and the frontend plan (01-04) can assert them verbatim.

- Stalled row warning (job log): must contain the lambda value, the phrase `no calibration was applied`, and the phrase `uncalibrated estimate`. Must NOT contain `not meaningful`, `unreliable`, `implausibly`, `falsely`, `omitted`, `7x` or `tight`.
- Ensemble-with-stalled-constituent warning (job log): must name each constituent with its lambda in the existing `name (lambda = value)` form, state that no calibration was applied to those constituents, and state that the ensemble point estimate is still a genuine fit. It must make NO claim about the width or the trustworthiness of the ensemble's intervals.
- `interval_note` for a stalled row: `no calibration was applied (lambda = <value>); the interval is the uncertainty of the uncalibrated estimate`.
- `interval_note` for a degenerate point-mass cell: `not calibrated; the interval is a point mass` (unchanged from today's `ci_omitted_reason` wording for that case).
- `interval_note` for a declined run (`calibration_declined`, from plan 01-01): `vacalibration could not calibrate this dataset; the values are uncalibrated`.
</wording>
