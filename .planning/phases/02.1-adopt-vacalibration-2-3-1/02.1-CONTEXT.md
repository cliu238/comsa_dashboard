# Phase 02.1: Adopt vacalibration 2.3.1 - Context

**Gathered:** 2026-09-12
**Status:** Ready for planning

<domain>
## Phase Boundary

The backend image installs vacalibration 2.3.1 from GitHub commit `498df45` while the
CRAN snapshot stays at 2026-08-01, every test suite passes without skips, and the
package's new sub-1 % / above-99 % exclusion rule is disclosed through the surfaces the
dashboard already has. No new capabilities: no new UI wording, no change to CI test
scope, no reply to the package author, no re-running of stored jobs.

Why now: CRAN published StanHeaders 2.39.1 on 2026-09-02 and vacalibration 2.2's Stan
models do not compile against it. Only the Phase 2 snapshot pin keeps the image
building; the snapshot cannot move until this phase lands.

</domain>

<decisions>
## Implementation Decisions

### Install and pinning
- **D-01:** Install vacalibration from GitHub pinned to the full commit `498df45`, never a branch or tag. `CRAN_SNAPSHOT` stays `2026-08-01`. Dependencies must not be upgraded by the install (e.g. `upgrade = "never"` with remotes, or a plain `R CMD INSTALL` of the archive tarball); the planner picks the mechanism. — **Reversibility:** reversible — switching back to the CRAN snapshot is the planned follow-up (seed `.planning/seeds/switch-vacalibration-pin-to-cran.md`).
- **D-02:** `backend/package-manifest.csv` changes `vacalibration,2.2` to `vacalibration,2.3.1`. The only other permitted manifest change is the installer package itself (e.g. `remotes`) if one is needed. Any other line change means dependencies drifted and the plan is wrong.
- **D-03:** `tests/test_dockerfile_pinning.R` gains an assertion that the vacalibration ref in `backend/Dockerfile` is a commit SHA; a branch name (`main`) or tag (`v2.3.1`) must fail the test. Existing snapshot assertions stay.
- **D-04:** The Dockerfile's Stan compile step is kept as is. 2.3.1 removed the bundled `seqcalib.rds`; our step compiles both models from source and writes the `.rds` files itself, so nothing depends on the bundled file.
- **D-05:** Keep installing `knitr`. The 2.3.1 DESCRIPTION still lists it under Suggests only, and the 2.2 runtime need was observed, not documented, so it is not proven gone.

### Behaviour under the widened `learn` rule
- **D-06:** Keep the dashboard's explicit zero-count `donotcalib` (`zero_count_causes()`, `build_donotcalib()`, `prepare_calibration_exclusions()` in `backend/jobs/utils.R`). Reason: `zero_count_causes()` is still what decides which causes the UI hides, and the explicit list is the only place the exclusion is logged. Add a comment at `build_donotcalib()` stating that, from 2.3.1 on, the package's learn rule (`puncalib < 0.01 | > 0.99`) reaches the same set independently and the two are unioned inside `vacalibration()`. — **Reversibility:** reversible.
- **D-07:** No new UI wording. Causes the package now declines under the sub-1 % rule are already surfaced by `not_calibrated_causes()` (reads `donotcalib_tomodel` and the pass-through signature) into the misclassification panel's "Not calibrated, so absent from this matrix" notice, whose wording is generic and stays correct. The "Excluded from calibration (no observed deaths)" notice in `JobDetail.jsx` is driven only by `zero_count_causes` and therefore stays correct too. The phase verifies this on a dataset with a 0-1 % cause; it does not add a per-cause reason.
- **D-08:** Record the vacalibration package version as one line in the job log at calibration time (e.g. via `packageVersion("vacalibration")` next to the existing exclusion log line). Nothing is added to the results payload, the CSV exports, or the UI. — **Reversibility:** reversible.

### Tests
- **D-09:** Test section 12c in `tests/test_vacalibration_backend.R` ("extracted matrix uses the 6 neonate broad causes") is fixed, not skipped: the expected cause set becomes the broad causes minus `not_calibrated_causes()` for that algorithm, which is what `normalize_mmat()` actually drops. This also closes the Phase 1 deferred item about learn-rule flakiness.
- **D-10:** Section 30b (issue #101 reproduction on `frontend/public/sample_eava_child.csv`) must keep passing unchanged: that file's smallest cause is 5.6 % of deaths, so the new rule excludes nothing extra and `malaria` stays calibrated.
- **D-11:** All suites run with zero skips: the R suite in full (real MCMC) locally against a local install of the same commit, the two dependency-free R suites, the frontend unit suite, and Playwright against a running backend. CI scope in `.github/workflows/test.yml` is unchanged (the vacalibration suite remains a stated local-only exclusion).

### Verification on the deployed stack
- **D-12:** Same acceptance shape as Phase 1: after the dev deploy, run a real job on the issue #101 sample file (child, Mozambique) and one job on a dataset containing a 0-1 % cause, and confirm the disclosures in D-07. The `deploy.yml` manifest diff must pass on the first build.

### Claude's Discretion
- Install mechanism (remotes with a SHA ref vs. archive tarball via `R CMD INSTALL`), subject to D-01 and D-02.
- How the pinning-guard test recognises a SHA (regex length/charset).
- Exact placement and wording of the version log line (D-08) and the redundancy comment (D-06).
- Whether the local full-suite run needs a helper to install the pinned commit locally; keep it out of the repo if it is a one-liner.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `backend/jobs/utils.R`: `zero_count_causes()`, `unobserved_causes()`, `build_donotcalib()`, `prepare_calibration_exclusions()` (input side); `not_calibrated_causes()`, `.declared_not_calibrated()` (reads `donotcalib_tomodel` rows), `.passthrough_not_calibrated()`, `normalize_mmat()`, `build_calibrated_map()`, `assemble_calibration_result()` (output side). All of these already handle the new exclusions without change.
- `backend/jobs/utils.R`: `is_broad_format()` / `build_broad_matrix()` bypass `cause_map()` for broad input and normalise spacing/case; keep using them even though 2.3.1's `cause_map()` now accepts broad names.
- `tests/test_dockerfile_pinning.R`: source-assertion guard over `backend/Dockerfile` (28 assertions), runs in CI without R packages; the natural home for D-03.
- `.github/workflows/deploy.yml` step "Verify backend package manifest (issue #123)": extracts `/opt/package-manifest.csv` from the built image and diffs it against the committed file.

### Established Patterns
- Every `install.packages()` in the Dockerfile runs with `options(warn=2)` so a failed install fails the build.
- The Dockerfile compiles both Stan models from `inst/stan/*.stan` at build and overwrites the `.rds` files; the package's own `get_stan_seqcalib()` compiles lazily from the `.stan` file if needed.
- Both job paths (`run_vacalibration()` in `backend/jobs/algorithms/vacalibration.R`, `run_pipeline()` in `backend/jobs/processor.R`) call `prepare_calibration_exclusions()` then `vacalibration(..., donotcalib = exclusions$donotcalib)` with the default `donotcalib_type = "learn"`; a source-level guard test fails if either stops delegating to the shared helpers.
- R suites use numbered `section()` blocks and `test()` assertions with `quit(status = 1)` on failure; `--input-only` skips MCMC sections.
- Exclusions are logged with `add_log(job$id, ...)`; the version line from D-08 belongs beside the "Excluding from calibration for <algo>" line.

### Integration Points
- `backend/Dockerfile` lines 74-77 (the openVA/EAVA/vacalibration/knitr install) and the manifest `required` vector at line ~116.
- `backend/package-manifest.csv` line `vacalibration,2.2`.
- `frontend/src/components/MisclassificationMatrix.jsx` lines 129-136 (the not-calibrated notice) and `JobDetail.jsx` lines 352-371 (zero-count and declined notices): verification targets for D-07, not edit targets.
- Local environment: rstan 2.32.7 + StanHeaders 2.32.10 match the image manifest; local vacalibration is 2.0 and must be replaced with the pinned commit to run the full R suite. The local R cannot run the plumber backend (no DBI/RPostgres), so Playwright needs the backend started per `.claude/skills/test`.

</code_context>
