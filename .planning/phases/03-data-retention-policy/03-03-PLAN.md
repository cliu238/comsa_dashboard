<objective>
Land the purge on master and prove on dev that it actually deleted the expired data, that nothing past
the window survives, and that a fresh job still works — then close issue #114 with the policy.

Purpose: everything before this plan is source-level. The deletion itself cannot be exercised locally
(`backend/db/connection.R` needs RPostgres and there is no local Postgres), so D-12 makes the deployed
stack the only place the behaviour is actually observed. This plan is also the one irreversible step in
the phase: roughly 240 stored jobs disappear with no backup.

Output: the two job inventories, the deploy run id and its per-job conclusions, the post-deploy
retention assertion, a fresh job id, and a closed issue #114.
</objective>

  initialises the pool on a fresh pod and therefore the request that fires the purge. It returns
  `{jobs: [...]}` with `id`, `type`, `status`, `algorithm`, `age_group`, `country`, `created_at`,

  against runtime output, so the checks below compare only the leading `YYYY-MM-DD` of each value and
  use lexicographic ordering, which is correct for both `"2026-09-13 04:34:51"` and ISO-8601 forms.
  Record the real format in the SUMMARY once seen (CLAUDE.md: verify formats against runtime output).

  no workflow prints pod logs. The `.claude/skills/comsa-postgresql` credentials are rotated, so the
  database cannot be queried directly either.
