<objective>
Make stored job data expire on its own: a single age-predicated DELETE against `jobs` that lets the
existing cascade do the rest, the matching pod-local directory removal, wired into main-server pool
init behind the existing worker guard and re-armed every 24 hours from inside the plumber process.

Purpose: this is the whole of ROADMAP criterion 2 ("expired job data is removed without manual
intervention"). Everything else in the phase either tells users about it or proves it on dev.

Output: `backend/db/retention.R`, a dependency-free `tests/test_retention.R` that fails before the
implementation exists, the three-line call site in `get_db_pool()`, `later` made an explicit image
dependency, and the new suite registered in CI.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plumber process -> `jobs` table | An unbounded or mis-predicated DELETE destroys live user data; there is no backup and no soft delete |
| purge loop -> pod filesystem | `unlink(recursive = TRUE)` on a path built from an id; a bad join addresses a shared parent directory |
| main server -> per-job worker processes | Both source `db/connection.R`; only the main server may run maintenance |
| Dockerfile install list -> built image -> deploy-time manifest diff | A changed resolved version fails the deploy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `retention_purge_sql()` age predicate | critical | mitigate | The statement is produced by one pure function whose output is asserted: exactly one `DELETE`, targeting `jobs`, `COALESCE(completed_at, created_at)`, strict `<`, `INTERVAL '<days> days'` interpolated from the one constant, and no second condition. `retention_purge_sql(7)` must contain no `90`, which is what proves the window is not hard-coded twice. |
| T-03-02 | Denial of Service | `remove_job_disk()` path construction | high | mitigate | Empty-id guard returns before `unlink()`, and a test asserts `data/uploads`, `data/outputs` and `data/jobs` survive an empty id with their contents, plus that a sibling job's directories are untouched. |
| T-03-03 | Denial of Service | purge raising during pool init | high | mitigate | `purge_expired_jobs()` and `schedule_purge()` each wrap their body in `tryCatch` with a `message()` handler, mirroring `cleanup_orphaned_jobs()`; asserted from source (D-08). The re-arm sits after the error-swallowing purge call, so a failed tick still schedules the next. |
| T-03-04 | Elevation of Privilege | per-job worker running the purge | medium | mitigate | The call sites live inside the single existing `COMSA_WORKER != "1"` guard; the suite asserts exactly one such guard in `connection.R` and both calls inside it. A worker also has no httpuv loop, so an escaped `later` tick would never fire. |
| T-03-05 | Repudiation | an unauditable first mass deletion | high | mitigate | `RETURNING id` plus one `message(sprintf(...))` line carrying the count and the ids; the format is asserted from source. Plan 03 captures the pre-deploy inventory so the delta is reconstructable even if pod logs are not retrievable. |
| T-03-SC | Tampering | adding `later` to the image install list | high | mitigate | No new package enters the image: `later,1.4.8` is already in `backend/package-manifest.csv` as a plumber transitive, resolved from the pinned 2026-08-01 snapshot. Guarded locally by a manifest assertion in `tests/test_dockerfile_pinning.R` and at deploy time by the blocking "Verify backend package manifest (issue #123)" step. No `[ASSUMED]`/`[SUS]` package, so no legitimacy checkpoint. |
| T-03-06 | Information Disclosure | purge log line contents | low | accept | The line carries job UUIDs and a count, no VA record content and no user email; it goes to the same server log that already records orphan cleanup ids. |
