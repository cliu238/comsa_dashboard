<objective>
Make the pinning enforceable at build time: extract the package manifest from the image the
pipeline just built, diff it against a manifest committed to the repository, and fail the run on
any drift.

Purpose: success criterion 4 ("building the same commit twice yields identical installed package
versions"). A committed golden manifest is a strictly stronger check than a one-off double build:
it asserts the property across every future build, not just two adjacent ones. It also pays for
itself during incident response — "what versions are actually in the running image" becomes a
file lookup instead of an archaeology exercise.

Output: three new steps in `.github/workflows/deploy.yml` plus an on-demand cache-free rebuild
switch. No change to application behaviour, the frontend build, or the deploy job.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ghcr.io → CI runner | The image being verified is pulled back across this boundary |
| built image → CI runner shell | `docker run` executes third-party-derived content inside a job holding `packages: write` |
| pinned snapshot → future time | A version set frozen today is served unchanged to builds run months from now |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Elevation of Privilege | The frozen 2026-08-01 snapshot eventually carrying a package version with a published CVE and no update path | accept | Pinning trades unbounded drift for bounded staleness, which is the intended trade for this phase. The committed manifest makes the exact deployed version set greppable, so a CVE announcement can be checked against the running image in seconds rather than by archaeology; and the snapshot date lives in one `ENV`, so advancing it is a one-line change plus a manifest refresh. A recurring advance schedule is explicitly deferred out of this phase. |
| T-02-07 | Tampering | Verifying a different image than the one just built (tag race) | mitigate | The verification pulls `${REGISTRY}/${BACKEND_IMAGE_NAME}@${{ steps.build-backend.outputs.digest }}` — the immutable digest emitted by the build step — never a mutable tag such as `:latest`. |
| T-02-08 | Elevation of Privilege | Running the freshly built image inside a job that holds `packages: write` | mitigate | The container is run with `--rm`, no volume mounts, no injected environment, and a single `cat` command; `GITHUB_TOKEN` is never passed into it. The job's `permissions` block is left unchanged at `contents: read` / `packages: write`. |
| T-02-09 | Repudiation | A vacuous pass — the manifest extraction silently producing an empty or truncated file that trivially matches, or matches nothing | mitigate | Before any comparison the step asserts the file is non-empty, that line 1 is exactly `Package,Version`, and that there are more than 100 data rows; any of these failing fails the step. The extracted file is uploaded as an artifact on `always()` so the evidence survives a failed run. |
</threat_model>
