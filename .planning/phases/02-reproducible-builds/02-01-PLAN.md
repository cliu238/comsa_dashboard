<objective>
Pin the backend build so that an unchanged commit resolves the same base image and the same R
package versions no matter when it is built, and make that property enforceable from source.

Purpose: issue #123. The 2-day outage in #122 happened because `RcppParallel` shipped a CRAN
release requiring `cmake` and the Dockerfile installs everything unpinned from
`cloud.r-project.org`. The breakage surfaced on a PR that had only touched `.R` files, so it was
misattributed to that PR. Pinning removes the class of failure, not just the instance.

Output: a digest-pinned, snapshot-pinned `backend/Dockerfile` that also emits an installed-package
manifest into the image; plus `tests/test_dockerfile_pinning.R` wired into the existing CI test
job as a regression guard.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| p3m.dev → build container | Untrusted third-party code (R package sources/binaries) enters the image here |
| Docker Hub / rocker → build container | The entire base OS and R runtime enter here |
| build container → runtime pod | Whatever was installed at build time is what serves authenticated user traffic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | `p3m.dev` snapshot host as build-time package source | mitigate | All 15 packages plus transitives resolve from one immutable dated snapshot over HTTPS; the base image is digest-pinned so the CA trust store and `download.file.method='libcurl'` are themselves fixed; `/opt/package-manifest.csv` records the exact resolved version set so a substituted version is detectable by diff (enforced in plan 02-02). |
| T-02-02 | Denial of Service | `p3m.dev` availability at build time | accept | If the host is unreachable the build fails loudly and no image ships; the running deployment is unaffected. Mirroring the snapshot into a private registry is disproportionate for a single-team dev cluster. |
| T-02-03 | Tampering | The `Rprofile.site` repo override | mitigate | The override is appended (`>>`), never overwritten, so the base image's `HTTPUserAgent` and `download.file.method='libcurl'` survive. If the override is ever lost, R falls back to the image's own 2025-04-10 snapshot, which lacks `vacalibration` and `EAVA` — the build fails rather than silently sourcing packages from an unintended repo. A test asserts the `>>` form. |
| T-02-04 | Spoofing | `sodium` backs password hashing (`backend/auth/passwords.R`) while being an implicit dependency | mitigate | `sodium` moves into an explicit `install.packages()` list AND into the build-time `stopifnot()` presence assertion, so its disappearance fails the build instead of failing at the first login attempt after a deploy. |
| T-02-05 | Information Disclosure | `/opt/package-manifest.csv` inside the shipped image | accept | It lists only package names and versions of a private image and contains no secrets. It does make CVE version-matching easier for anyone who obtains the image, but the same information is derivable from the public `backend/Dockerfile` and the pinned snapshot date. |
</threat_model>
