<objective>
Prove on the real build platform that the pinning works, and freeze the resulting version set into
the repository so every future build is checked against it.

Purpose: success criteria 1 and 4 cannot be closed from a developer machine. The dev machine is
arm64 and the runner is amd64, so a local `docker build` is not a verdict. Equally, "the deploy
went green" is not a verdict — `deploy.yml` has a `check-changes` path filter, and the #122
post-mortem is precisely a case where the overall workflow reported success while the backend
image was never built. This plan reads per-job conclusions and requires an uncached rebuild.

Output: `backend/package-manifest.csv`, committed, and two green workflow runs whose per-job
conclusions have been read individually.
</objective>

<interfaces>
Facts this plan depends on, established by the earlier plans in this phase:

- `backend/Dockerfile` writes `/opt/package-manifest.csv` inside the image: a `write.csv(...,
  row.names = FALSE, quote = FALSE)` of `installed.packages()[, c("Package", "Version")]`, sorted
  under `LC_COLLATE=C`. Its first line is exactly `Package,Version`.
- `.github/workflows/deploy.yml` extracts that file from the built image by digest, uploads it as
  workflow artifact `backend-package-manifest`, and diffs it against `backend/package-manifest.csv`.
  While that file is absent the step is advisory (loud notice, exit 0). Once it exists the step is
  blocking (exit 1 on any difference).
- `.github/workflows/deploy.yml` accepts a `workflow_dispatch` boolean input
  `force_backend_rebuild` that sets `no-cache: true` on the backend build and forces it to run
  regardless of the `check-changes` path filter.
- The `check-changes` filter watches `backend/**`, so committing `backend/package-manifest.csv`
  does itself trigger a backend rebuild. That is deliberate.

Versions independently verified in the 2026-08-01 snapshot on 2026-08-25 — the manifest must agree
with all fifteen or something is wrong: vacalibration 2.2, EAVA 1.0.0, openVA 1.2.0, sodium 1.4.0,
plumber 1.3.3, jose 2.0.0, pool 1.0.5, knitr 1.51, rstan 2.32.7, RcppParallel 6.2.0,
RPostgres 1.4.10, uuid 1.2-2, future 1.75.0, jsonlite 2.0.0, rJava 1.0-18.

`gh` is installed and authenticated in this environment. `gh run view <id> --json jobs` returns
each job's `name` and `conclusion`; a job that did not run has conclusion `skipped`, which for the
purposes of this plan is a failure, not a pass.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI run → repository | A workflow artifact is promoted into a committed file that governs all future builds |
| CI report → human judgement | An overall workflow status is read as evidence about what was actually built |
| new image → live users | The rebuilt image serves authenticated traffic on k8s-dev |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-14 | Repudiation | Treating an overall-green workflow as proof when the backend build was `skipped` — the documented #122 failure mode | mitigate | Every acceptance criterion reads per-job conclusions via `gh run view --json jobs` and names `skipped` as a failure. The overall run status is never used as evidence. |
| T-02-15 | Tampering | Committing a golden manifest that does not reflect the pinned snapshot, freezing a wrong version set into the enforcement gate | mitigate | The artifact is downloaded from the same run whose digest-pinned build produced it, and before committing, all fifteen load-bearing versions are asserted against values verified independently on 2026-08-25. Any mismatch stops the task rather than updating the numbers. |
| T-02-16 | Spoofing | `sodium` moved from transitive to explicit; if that install silently failed, password verification breaks only at first login | mitigate | Two independent checks: the build-time `stopifnot()` in the Dockerfile's manifest step, and a runtime login against the deployed pod in Task 3's acceptance criteria. The manifest itself also records `sodium,1.4.0`. |
| T-02-17 | Tampering | The manifest records versions but not content hashes, so a package re-released under the same version number would pass the diff | accept | Posit p3m snapshots are immutable by date, so same-version content substitution would require compromising the snapshot host itself. Per-package hashing exceeds this phase's scope and has no in-repo consumer. |
